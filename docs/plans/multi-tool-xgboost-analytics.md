Multi-tool repository and XGBoost analytics implementation plan

Implementation status: the multi-tool structure and XGBoost dashboard are built.
Open `index.html` for comparison or `xgboost-analytics.html` for analytics. The
architecture and scope below record the implementation plan; current build and
test commands are documented in `README.md`.

The implemented interpretation of “final timestep” is a report covering all payment
decisions in a completed scenario, with individual payments available for
inspection, following the scope used when implementation was requested. There is no
playback, stepping, rewind, timeline scrubber, or pending-payment view in the new
tool. Historical feature construction still processes events chronologically
once, because each prediction depends on the history preceding its payment.

The first version analyzes the existing tree checkpoint and existing scenario
generator. It explicitly uses supervised tree scoring and observed-history
execution (`trainingMode: 'supervised'`, `mode: 'shadow'`). The comparison tool
continues to support its existing model modes and blocking simulations.

Repository findings at planning time that determined the design:

- `build.py` assembles one template, one model bundle and one UI into an offline
  page. `index.html` is generated output; edits belong in source templates.
- `model.js`, `model-adapters.js`, `policy.js` and `scenarios.js` already form a
  reusable runtime. `comparison.js` combines multi-model orchestration with
  reusable evaluation metrics. `ui.js` owns the comparison interface.
- `designs.json` registers models, not tools. Tool registration needs its own
  small manifest.
- The XGBoost checkpoint is a custom NumPy-trained, XGBoost-compatible booster:
  32 trees, depth at most three, and 27 input features. It is not native XGBoost
  model JSON. Its no-label mode bypasses the trees and evaluates a rarity formula.
- Predictions expose feature values and probability, but the saved decision
  records discard them. The preview cache retains only eight predictions.
- Exported trees have split thresholds and leaf values but no reference counts
  for SHAP, gain statistics, or explanation baseline.
- Build, training, validation signatures and tests contain root-relative paths.
  Moving files must update these together.

   Preserve the existing model, dataset and JSON artifact paths in this first
   refactor. Keep root `build.py` and `train.py` as small command entry points so
   documented usage still works. Retain the parent-directory comparison fragment
   generated by the current builder for compatibility.

   Keep `index.html` as the comparison entry point and generate
   `xgboost-analytics.html` alongside it. Both pages get shared navigation with
   relative links. Each tool remains a self-contained file that can be opened
   directly; its title and model data are supplied by the builder. Common
   navigation must remain usable without a server or network connection. The
   current shell references CDN tooltip and icon helpers; inline or replace any
   helpers needed by the pages so explanations remain accessible offline.

   Each registry entry declares a stable ID, label, template, script order,
   model IDs and output filename. A build loop validates and assembles entries.
   Adding a third tool should require its directory and a registry entry.
   Keep shared code independent of tool code and isolate DOM IDs and page state.

   Move the comparison code first, preserving behavior. Extract `metrics()` into
   `shared/runtime/metrics.js`, then extract the existing XGBoost feature and
   tree evaluation helpers into `shared/runtime/xgboost.js`. Both tools use the
   same scoring helpers. The analytics page embeds only the XGBoost checkpoint
   and runs only that model.

   Update imports, test fixtures, Python root resolution, embedded Node commands,
   policy-validation source signatures and documented commands. Centralize the
   build dependency lists so tests and manifests do not maintain conflicting
   script orders. Model weights remain unchanged; regenerated policy frontiers
   must remain numerically identical after path and provenance changes.

2. Add a completed-run analytics result.

   Add an analytics collector that uses the shared score-before-update and
   decision-policy behavior. It processes the full scenario in cancellable
   chunks and publishes the completed result atomically. It needs no rewind
   snapshots or playback state. Prefer a small optional capture hook in the
   runner, or a forward collector around the existing core functions, over
   duplicating scoring, settlement or threshold logic.

   Store the run configuration, checkpoint hash, feature-schema version, scenario
   identity, final event position/time, final policy state and final metrics.
   For every payment, retain an immutable record containing:

   ```text
   event ID, timestamp, sender, recipient, amount
   all 27 model inputs and their readable values
   raw tree margin, probability, score in bits
   threshold used at that payment, decision, settlement status
   explanation reference ID
   ```

   Join evaluation outcomes separately by event ID after scoring. Deposits and
   reports update the history but do not become payment predictions. The final
   event can be a deposit or report, so completion must not depend on a final
   payment preview being available.

   Retain each payment's original threshold (`tauBefore`). The final learned
   threshold describes the completed run; applying it retrospectively to every
   payment would produce different decisions. Never recompute an earlier
   payment's features from final account state.

   Reuse the existing policy choices for the single model: shared budget, fixed
   threshold, historical cost tuning and historical automatic objective. Start
   with existing shared-budget defaults (2%, 128 warm-up requests), and disable
   historical tuning choices when their validation data is absent. Policy
   changes rebuild the decision report; observed-history scores can be reused.
   Dataset changes require a new forward run. Filters, sorting and payment
   selection only operate on completed results.

3. Make every feature contribution inspectable and verifiable.

   Add a feature dictionary matching the checkpoint's ordered feature list.
   For each feature, provide its label, definition, source, unit, transformation
   and history window. Distinguish transformed model inputs from readable counts,
   amounts, gaps and ratios. “Recent” features use the preceding 60 minutes;
   gaps measure time since the account's last observed activity under the
   existing implementation. Preserve first-activity and denominator-floor
   semantics in both code and descriptions.

   Export a versioned explanation sidecar from the existing trees and historical
   fitting partition. Reconstruct the same causal feature rows, route the
   labeled fitting rows through each tree, and record node reference counts.
   Unknown outcomes still participate in history construction. Hold-out episodes
   and scenario evaluation outcomes do not define this reference population.
   This export requires no model retraining.

   Record the checkpoint hash, history hash, split, feature schema and reference
   convention. Use unweighted fitting-row counts explicitly; do not describe
   these as native XGBoost Hessian cover. Reject stale or incompatible explanation
   data. Include the sidecar in the normal build freshness checks.

   Implement exact path-dependent TreeSHAP over this declared count convention.
   Validate it against an independent exhaustive Shapley calculation on small
   trees, including repeated-feature splits. For each payment:

   ```text
   reference expected margin + sum(feature contributions) = raw tree margin
   probability = existing clipped sigmoid(raw tree margin)
   score in bits = -log2(max(1e-12, 1 - probability))
   decision = existing policy applied to score and original threshold
   ```

   Include the learning rate in tree contributions. The reference expected margin
   includes expected tree outputs as well as `base_score`. Contributions add in
   log-odds; probability and bits are separate transformations of the total.
   Positive contributions raise the model output and negative contributions lower
   it relative to the reference. They explain model behavior, not causal effects.

   The official [SHAP TreeExplainer documentation](https://shap.readthedocs.io/en/stable/generated/shap.TreeExplainer.html)
   describes path-dependent reference counts and raw log-odds output. Native
   XGBoost likewise exposes additive margin contributions in its
   [prediction API](https://xgboost.readthedocs.io/en/stable/python/python_api.html).
   Our custom checkpoint needs its own compatible explanation implementation.

   Keep all 27 features visible, including zero-contribution features. Compute
   global importance as mean absolute contribution over the displayed population;
   expose that population and sample count. Cache attribution rows against the
   checkpoint, reference and captured feature row. Do not substitute split
   frequency or a leaf-path heuristic for feature attribution.

4. Build the XGBoost analytics interface.

   Use three linked views backed by the same completed result:

   | View | Contents |
   | --- | --- |
   | Overview | Scenario, size and seed; single-model policy controls; total payment count, assessed count, warm-up count, blocks, block rate, precision, recall and F1; confusion matrix; score distribution with allowed/blocked cohorts. |
   | Features | Mean absolute SHAP ranking for all features; contribution distribution colored by feature value; feature value versus contribution plot; searchable definitions and feature statistics. |
   | Decisions | Searchable and sortable payment table with account, amount, score, original threshold, decision and known outcome; filters for false positives, false negatives, allowed, blocked and warm-up payments. |

   Selecting a payment opens its inspector: prediction and original decision,
   contribution waterfall, all-feature table with readable/model values, and
   a tree selector that highlights the actual split path and weighted leaf
   contribution. Default to an inspectable payment after completion and allow
   selecting any other record without processing events again.

   Keep labels and metrics explicit. Classification metrics use known outcomes
   and exclude warm-up; block rate excludes warm-up but includes unlabeled
   assessed payments. Show the denominators and display unavailable metrics as
   such. The analytics presentation should mark classification metrics as
   unavailable when there are no assessed labeled payments, without changing
   shared F1/F2 conventions or the comparison's behavior. Report model probability as an
   uncalibrated estimate. For a changing online cutoff, show original decisions
   in distributions; a single final-cutoff line must not imply it produced all
   historical decisions.

   Display loading, progress, cancellation and empty/error states. Filtering
   updates the feature population and its count consistently. Provide accessible
   text and tables alongside charts, keyboard-accessible selection and responsive
   layouts. Export the completed decision table as CSV and the versioned report
   with configuration, feature values and contributions as JSON.

5. Verify and deliver in reviewable increments.

   First deliver the repository refactor with the existing comparison behavior
   intact. Run the existing policy, comparison/parity, core logic, UI and
   responsiveness checks from their updated locations; check training imports
   and the gradient suite after moving training code. Build and open the offline
   comparison page. Establish a numerical baseline before moving files.

   Next deliver the analytics collector and explanation export/engine. Confirm
   final predictions, decisions and metrics match the shared runner on fixed
   scenarios and seeds. Verify attribution additivity, zero unused-feature
   contribution, repeated split behavior and threshold equality (`score > tau`).
   Confirm later payments/reports cannot change captured earlier feature rows or
   explanations, and that incompatible reference metadata is rejected.

   Finally deliver the dashboard and exports. Verify all 27 features are
   accessible, filtered populations agree across charts/tables, cancellation
   cannot publish stale reports, and all comparisons/explanations work offline.
   Test an ending nonpayment event, all-warm-up and empty-filter cases, unknown
   outcomes and an all-benign scenario. Measure completion and attribution work
   on the largest existing fixture; keep work chunked and selection/filtering
   independent of model inference. Inspect real-browser layout in addition to
   the repository's lightweight DOM tests.

   Completion means both tools build from shared sources, the current comparison
   retains its behavior, and the new page provides a completed-run report with
   global and per-payment explanations that reproduce its XGBoost predictions.

Native XGBoost checkpoint import, training controls, SHAP interaction matrices,
counterfactual editing and enforcement simulations are later extensions. The
initial implementation should establish accurate explanations and a reusable
multi-tool structure before extending the model or analysis scope.

Validation now includes the original regression baseline, independent Python/JS
explanation oracles, completed-run parity and policy-cache checks, and a real
offline browser suite covering desktop/mobile layouts and the inspection flows.
Node was provisioned outside the repository for these checks. The working
checkpoint updates made during implementation are preserved in the rebuilt pages.
